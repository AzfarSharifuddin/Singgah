# Vendor management — Sprint 5

The new [admin management](admin-management.md) feature supersedes this sprint's
statements that approval is available only through database tooling. Vendor
ownership and customer session boundaries remain as described below.

## Routes and flow

- `/vendor/register`: email/password account creation, minimum 12-character password.
- `/vendor/login`: confirmed email/password sign-in and generic credential errors.
- `/auth/callback`: exchanges the email confirmation PKCE code for a vendor session.
- `/dashboard`: status, live published rating/count, product count and public link.
- `/dashboard/onboarding`: business, structured location and optional contacts in one form.
- `/dashboard/profile`: edit the same fields without changing the established slug.
- `/dashboard/products`: create, edit and deactivate products; primary image upload.
- `/dashboard/products/new` and `/dashboard/products/[id]/edit`: focused product forms.
- `/dashboard/photos`: logo, cover, up to eight gallery photos and image removal.

Registration creates only an Auth account. A confirmed account with no business
is directed to onboarding. Saving onboarding creates a pending business and opens
the optional branding step. Finish opens the overview. No multi-step framework,
multi-business support, staff management or role hierarchy is introduced.

New businesses remain **pending**. A platform operator must approve the exact
business through trusted administrative database tooling before it becomes public.
The dashboard explains the pending state and does not offer a public link until
the business is published and active. Owners cannot change approval, activity,
ownership or slug fields. The browser tests use scoped admin approval of temporary
fixtures only. There is no admin moderation UI.

## Authentication and customer separation

`@supabase/ssr` supplies a separate `singgah-vendor` cookie session. Cookies are
HttpOnly, SameSite=Lax and Secure in production. Server actions and pages validate
the user with Supabase `getUser`, reject anonymous or unconfirmed users, and
derive the business through `current_vendor_id()`. The proxy persists refreshed
cookies on all routes that read the vendor session, including the review gate.
Authenticated responses are private/no-store. Use HTTPS for production auth.

Sprint 4's customer session remains in its original browser-local storage key.
Vendor login/logout neither replaces nor removes it. While a registered vendor
cookie session is active, both the review page and submission API ask the user to
sign out before using their separate customer identity. There is no automatic
conversion/linking of anonymous accounts and no implied Verified Visit. Clearing
cookies/storage still has the existing anonymous-identity limitations.

The application role is ownership itself: a confirmed, non-anonymous account may
create one business. `auth.users` supplies trusted anonymous/confirmation state;
editable `user_metadata` is never used for permissions. Admin operations remain
outside the app. No extra roles/profiles table is necessary yet.

## Database/RLS

Migration `20260927000100_vendor_management.sql` adds:

- A unique non-null owner index, enforcing one business per account.
- Private helpers for confirmed-account eligibility, ownership and media paths.
- `current_vendor_id()` and `create_vendor_business(jsonb)` scoped RPCs.
- Owner SELECT policies for the owner's pending business, products and media.
- Column-limited profile UPDATE permissions with ownership RLS.
- Product INSERT/UPDATE permissions with ownership RLS, and no DELETE permission.
- Narrow media attach/detach RPCs, Storage bucket and Storage policies.

Onboarding derives `owner_user_id` from `auth.uid()` and always sets pending status.
It rejects unexpected JSON fields. Slugs are generated by the database, reserved
route names are avoided, and a collision gets a UUID suffix. Transaction advisory
locks serialize the same owner/name; database uniqueness remains the final guard.

Profile/product forms validate lengths, IDs, prices, safe web URLs and contact
format on the server. Composite FKs continue to enforce category/subcategory and
state/city/area consistency even for direct API calls. Owners cannot choose another
vendor ID through UI actions; RLS also rejects direct cross-vendor mutations.
The existing public read policies and review permissions remain intact.

Product prices are optional non-negative MYR values with at most two decimal
places. Deactivation preserves historical ratings. No inventory, checkout, SKU,
hard deletion or advanced catalog behavior is present.

## Storage and image lifecycle

The `vendor-media` bucket is **private**, with a 3 MiB per-object limit and JPEG,
PNG and WebP MIME allowlist. This preserves the approval model: pending/suspended
vendor media cannot get new public signed URLs. A public bucket would expose all
objects regardless of those database publication rules.

```text
vendors/{vendorId}/logo/{uuid}.webp
vendors/{vendorId}/cover/{uuid}.webp
vendors/{vendorId}/gallery/{uuid}.webp
vendors/{vendorId}/products/{productId}/{uuid}.webp
```

Storage INSERT/SELECT/DELETE policies validate the path against `auth.uid()`'s
owned business. Product paths must reference an actual product of that business.
There is no overwrite/UPDATE policy. Public reads require matching public image
metadata, an active published business, and an active product where applicable.
The existing profile's signed-URL implementation is reused without a duplicate
public profile renderer. Owners can read their own pending media in the dashboard.

Uploads go through server actions using the owner's JWT, never a service-role key.
Files must be at most 3 MiB, have an allowed declared MIME and match the decoded
image format. `sharp` rejects malformed/animated images and excessive pixel counts
(20 million); it corrects orientation, strips metadata, resizes to at most 512px
for logos or 2048px for other images, and emits WebP. Server Action requests are
bounded at 4 MiB; the extra space allows multipart fields around a valid 3 MiB file.
Extremely oversized requests can be rejected by Next before the friendly form
validator; the normal 3 MiB validation path is browser-tested.

Replacement uploads a new UUID object, attaches it through a transaction-locked
RPC, then deletes the old object. A failed attach attempts to delete the new upload.
The gallery cap is enforced inside the RPC, not only in the UI. Removal detaches
metadata, then deletes the Storage object. SQL and Storage cannot share a transaction,
so failures produce a clear cleanup message. **Clean unused uploads** removes
unreferenced objects older than ten minutes, up to 1,000 per known folder per pass.
Run it again if a large interrupted-upload backlog exceeds that pilot-scale bound.

Already issued signed URLs can remain usable until expiry (ten minutes), and
browser/CDN caches can retain previously fetched images after replacement/deletion.
New references always use fresh paths. Publication changes prevent new signatures;
they do not retroactively revoke a previously issued URL. No attempt is made to
delete Storage object rows directly via SQL.

## Account configuration and current email blocker

Email/password and email confirmation are enabled. In Supabase Authentication:

1. Add `http://127.0.0.1:3002/auth/callback` to **URL Configuration → Redirect URLs**
   for this development preview, and the exact HTTPS callback for deployment.
2. Configure **Email / SMTP Settings** with a real mail provider for general vendor
   registrations. The default sender is intended for limited testing and restricts
   recipients; it has a low project email quota.
3. Keep email confirmation enabled. Open confirmation links in the browser where
   registration began for seamless PKCE sign-in. If confirmation happens in another
   browser, the email may be confirmed but the local PKCE exchange cannot finish;
   return to the login page and use email/password.

The authorized real-email registration test currently returns
`over_email_send_rate_limit`; no confirmation email was sent and no test account
was created. Email delivery, confirmation and callback completion remain unverified
until the quota recovers or custom SMTP is configured. The application displays a
friendly retry-later message. We did not disable confirmation or change account
settings to make tests pass.

References: [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client),
[email limits](https://supabase.com/docs/guides/auth/rate-limits),
[custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

Production Turnstile setup remains outside Sprint 5. Review protection remains
enabled as before. If global Supabase Auth CAPTCHA is enabled later, vendor
signup/password login must also supply its CAPTCHA token; these vendor forms do
not yet include that deployment integration. Do not enable it without completing
that follow-up. No production keys, OAuth or email-provider credentials are stored.

## Tests and known limits

```text
npm run test:vendor-management
npm run test:vendor-management-db
npm run test:vendor-storage
npm run test:vendor-management-browser
```

The DB suite uses rollback-only synthetic identities. The Storage and browser
suites create temporary confirmed Dev accounts with random passwords and verify
actual Supabase password login. They do **not** claim to verify email registration.
Tests clean up only their exact account IDs, businesses, products and Storage
objects. `PLAYWRIGHT_MODULE` points to an existing Playwright runtime and Edge;
`TEST_BASE_URL` defaults to port 3002, and optional `SCREENSHOT_DIR` is outside Git.

`check-vendor-registration.mjs register|verify` is separate and requires an
explicitly authorized real email (`TEST_VENDOR_EMAIL`) and a private temporary
state path (`TEST_VENDOR_STATE`) outside Git. It refuses an existing account. Do
not run unsolicited email tests. The human recipient must open the confirmation
email; the agent then verifies login and removes the exact temporary account.

Verified: 21 ownership/RLS/slug checks; real Storage valid/invalid MIME/oversize
uploads, cross-owner denial, pending/private vs public signed reads, replacement
and deletion; complete confirmed-account dashboard flows at 375px and 1280px,
including wrong password, redirects, persistence, onboarding, editing, all four
image types, public rendering, product deactivation, logout and retention of a
real anonymous customer session. No console/runtime errors or horizontal overflow
occurred in completed dashboard scenarios.

The dashboard has no review management page: public published reviews remain
available on the existing profile, and owners have no moderation powers. Review
replies/reporting, gallery reordering, password reset UI, profile autosave, multiple
staff/businesses, admin UI, analytics and NFC tracking are deferred. Unsaved form
values survive validation failures but not deliberate navigation away. Retention,
per-account upload quotas and operational mail monitoring are deployment work.
